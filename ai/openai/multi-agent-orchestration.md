# 多智能体编排与交接（Orchestration and Handoffs）

## 核心概念

多智能体工作流的首要设计决策是：**谁拥有面向用户的最终回复**。

## 两种编排模式

| 模式 | 特点 | 使用场景 |
|------|------|----------|
| **交接（Handoffs）** | 控制权转移给专家 | 专家应该拥有下一个回复 |
| **智能体作为工具（Agents as Tools）** | 管理者保持控制权 | 管理者需要综合答案、专家执行有限任务、需要稳定的外部工作流 |

### 交接模式（Handoffs）

**核心思想**：像"转接电话"一样，把对话完全交给专家。

**适用场景**：
- 专家应该拥有下一个回复，而非仅仅在幕后帮助
- 需要专家直接与用户交互
- 任务可以完全委托给专家

**代码示例**：
```python
from agents import Agent, handoff

billing_agent = Agent(name="账单智能体")
refund_agent = Agent(name="退款智能体")

triage_agent = Agent(
    name="分诊智能体",
    handoffs=[billing_agent, handoff(refund_agent)],
)
```

**最佳实践**：
1. **给每个专家分配狭窄的职责** - 每个专家只做一件事
2. **保持交接描述简短具体** - 清楚说明何时转交
3. **只在必要时拆分** - 只有当需要不同的指令、工具或策略时才拆分

**高级功能**：
- 可携带结构化元数据（传递上下文信息）
- 可携带过滤后的历史（只传递相关对话）
- API 因编程语言而异，参考 SDK 文档

### 智能体作为工具模式（Agents as Tools）

**核心思想**：管理者像"使用工具"一样调用专家，但保持控制权。

**适用场景**：
- 管理者应该综合最终答案
- 专家执行有界限的任务（如总结、分类）
- 需要一个稳定的外部工作流，嵌套专家调用而非所有权转移

**特点**：
- 管理者始终保持控制权
- 专家只返回结果给管理者，不直接接触用户
- 管理者可以整合多个专家的意见

## 设计原则

### 从简单开始
尽可能从一个智能体开始。只有当专家能实质性改善以下方面时才添加专家：
- 能力隔离（Capability isolation）
- 策略隔离（Policy isolation）
- 提示清晰性（Prompt clarity）
- 追踪可读性（Trace legibility）

### 避免过度设计
过早拆分只会：
- 增加更多的提示
- 增加更多的追踪
- 增加更多的审批界面
- 不一定能改善工作流

## 对比总结

| 维度 | 交接模式 | 智能体作为工具 |
|------|----------|----------------|
| **控制权** | 转移给专家 | 保留在管理者 |
| **用户交互** | 专家直接对用户 | 管理者对用户 |
| **适用场景** | 专家独立处理 | 需要整合协调 |
| **类比** | 转接电话 | 顾问团队 |
| **灵活性** | 专家自主决策 | 管理者统一决策 |
| **一致性** | 可能风格不一 | 保持统一风格 |

## 如何选择

**选择交接模式**：
- 需要专家直接与用户深度交互
- 任务可以完全委托给专家
- 不同分支需要不同的对话风格

**选择智能体作为工具**：
- 需要综合多个专家的意见
- 保持统一的用户体验
- 管理者需要审核或加工专家输出
- 任务需要多步骤协调
